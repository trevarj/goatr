# Heeler Android rewrite: studio-first review gate

## Context
The user reports that the current Goatr application is unacceptable and non-functioning and requests a complete Android rewrite matching Heeler's visuals and behavior, except for underlying libraries and explicitly selected platform/transport differences. Research and several question rounds established the target below. The user then explicitly selected **a localhost web studio containing reference screenshots and annotated wireframes, delivered for their review before any production UI rewrite**. This approval therefore executes the studio/rewrite-contract gate only; the full application remains required, but production implementation must wait for that review and a subsequent implementation handoff, not be presented as completed by this studio.

The selected backend is now **herdr-core only**: Android is a native core client over an authenticated, authorized paired iroh stream to an exact host-configured **already-running** core client Unix socket/session. Adopt existing sessions and terminals created by **any native hc client**, not only Goatr-created resources. This is a design-contract/studio pivot, not a production implementation or runtime-version/install decision. The Heeler visual pin and studio-first review gate remain unchanged.

### 5. Put the actual rewrite architecture and acceptance sequence in the studio
This is required review content, not permission to start production implementation before the user review. Show the following concrete choices and evidence alongside the feature catalog so the studio is not just an attractive mood board.

**Architecture to carry into the later implementation plan:**
- One application-owned runtime/connection/store, preserving useful `GoatrRuntime` ownership and `StateFlow` behavior; Views observe it rather than creating a second endpoint/store. Requalify `SecretStore`, genuine pairing, native IME, no-replay/recovery and strict framing. Compose-specific state must be removed together with all callers, not just its Gradle plugin.
- Linux Rust companion is only an authenticated/authorized **native-byte bridge** to the exact host-configured existing core client Unix socket; host may explicitly expose endpoint selections, never a client-supplied arbitrary path/destination. Pairing/peer authorization precedes opening/forwarding each socket. Close actual active iroh streams/connections **and matching socket handles** on revocation/replacement; refuse new streams. Bound forwarding buffers/backpressure; no companion-owned PTY, terminal projection/history, provider runtime, additional remote shell/filesystem protocol, new SSH or public TCP.
- Connect directly to the existing socket. Never launch `hc connect` or ordinary CLI probes to connect/detect: they call `connect_or_start`, and `hc connect` has no no-autostart option. Unavailable/mismatched core means a truthful failed selection, not an autostart/install or silent substitute.
- Android sends newline JSON-RPC 2.0 `hello {generation:1, framed:true}`; **the reply is still newline JSON**, framing starts afterward. Inspect generation, returned `core.id/name`, advertised methods/features; require actually used `framed/attach/events/status`. Native header is **9 bytes** `[channel u32 LE][kind u8][length u32 LE]`, payload max **16 MiB**. Preserve DATA/CREDIT/CLOSE/RESIZE/FOCUS/FACTS; **256 KiB** initial stream credit, acknowledged only after consumption/rendering. Parse event JSON lines incrementally across DATA frames; RPC replies may reorder. `AUTOMATIC_INPUT` kind 6 needs both hello feature and attach confirmation, otherwise DATA; tag generated replies at source. Observer `resize_notifications` also needs attach negotiation, apply RESIZE before following DATA or track size events if unavailable.
